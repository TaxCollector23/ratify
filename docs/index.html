Documentation

Ratify turns the engineering standards your repository already has — the ones that live in architecture discussions, PR reviews, and the memory of senior engineers — into executable doctrine, and evaluates every pull request against that doctrine before a human reviewer gets involved. This document explains how it works, from installation through feedback.

Status: Ratify is live and reviewing real pull requests. The GitHub App is github.com/apps/ratify-reviews. The public dashboard is at ratify-zeta-dusky.vercel.app/dashboard.

What Ratify is

Ratify is a repository-aware pull request reviewer. It runs three passes on every PR:

  1. Deterministic policy checks. Fast, cheap, zero hallucination risk. See the full list.
  2. Repository doctrine retrieval. Pulls in the rules mined from this repository’s own history so the reviewer reasons against your standards, not generic best practices.
  3. Model reasoning. A model reads the diff plus the deterministic findings plus the doctrine and returns structured findings with severity, confidence, and a per-finding rationale.

Findings are posted as a GitHub check run and a PR comment, and every stage of the pipeline is recorded in a timeline you can inspect at /dashboard/{sessionId}.

Quickstart

Three steps, roughly two minutes:

  1. Create a Ratify account at /signin. Sign in with email + password. During sign-up, enter the GitHub username or organization you’ll be installing on — this is how we auto-link the installation to your Ratify account.
  2. Install the GitHub App at /install. Pick the repositories you want reviewed. Read access to code, write access to checks & PR comments — nothing else.
  3. Open a pull request on any connected repo. Within a few seconds you’ll see a Ratify check run appear, plus a PR comment if any findings landed. The full review, evidence, and pipeline timeline are visible at /dashboard.

Installing the GitHub App

The install button on /install takes you to github.com/apps/ratify-reviews/installations/new. There you:

  • Choose the account (personal or organization) to install on.
  • Choose All repositories or Selected repositories. You can change this later in your GitHub App settings.
  • Grant the requested permissions.

GitHub calls Ratify’s installation webhook the moment you finish; the installation and its repositories are persisted to Ratify’s database. If your GitHub username matches the one you gave at sign-up, the installation is auto-linked to your Ratify account and shows up on your dashboard immediately.

Linking your account

Auto-linking works when the GitHub account you install on has the same login as the value you typed on the Ratify sign-up form. If they differ (e.g. you signed up as @you but installed on @your-org), sign back in and re-enter the org handle. All unclaimed installations with a matching login link on the next request.

The review pipeline

When GitHub sends a pull_request event, Ratify runs this sequence:

webhook_received
  → context_retrieved   (fetch changed files from GitHub API)
  → policy_checks       (deterministic rules; see below)
  → llm_call            (model reasoning over diff + doctrine + policy findings)
  → evidence_generated  (score risk, cluster findings)
  → published           (create check_run + PR comment)

Every stage is timestamped in the review_events table with its duration and stage-specific detail. That entire event log is rendered on the review detail page, so you can see exactly what the pipeline did, how long each step took, and why a finding was raised.

Duplicate webhook deliveries (GitHub retries up to 8 times over 24 hours if we’re slow) are dropped at insert time by a unique index on (pull_request_id, head_sha) and logged as skipped_duplicate, so you never get two parallel reviews or two PR comments for the same commit.

Deterministic policy checks

These run before any model call. They’re fast, high-precision, and give no hallucinations. Adding more rules is the single highest-leverage thing we can do to improve review quality — every deterministic check is one fewer thing the model has to remember.

Rule keySeverityFires when
missing-tests-for-payments-pathshighA file under a payment/billing/checkout path changed and no test file changed in the same PR.
secret-in-diffhighAn added line matches a high-precision pattern for a real secret: AWS keys, GitHub PATs, OpenAI/Anthropic keys, Slack tokens, PEM-encoded private keys, Google API keys.
removed-test-filemediumA file matching the repo’s test-path pattern was deleted.
dependency-change-detectionmediumA dependency manifest (package.json, pnpm-lock.yaml, requirements.txt, go.mod, Cargo.toml, Gemfile) changed.
migration-addedmediumA file under a migrations/ or drizzle/ path was added.
direct-db-access-in-handlermediumA file on an api/handlers/routes/controllers path issues a raw database call in the diff.
swallowed-catchmediumAn empty catch(...) {} block was added.
hardcoded-localhostmediumA hardcoded http://localhost or http://127.0.0.1 URL was added outside test/doc paths.
large-single-file-changelowA single non-lockfile changed more than 500 lines.
todo-debug-codelowAn added line contains TODO, FIXME, console.log, or debugger.

Repository doctrine

Doctrine is the set of rules that describe how this specific repository is meant to be built — not generic engineering advice. Rules are inferred from patterns in review comments, merged PRs, and repository documentation, and stored as structured, confidence-scored assertions with these attributes:

  • Rule text. A short imperative statement (“Integration tests are required for payment logic.”).
  • Category. Architecture, testing, documentation, dependencies, observability, etc.
  • Strength. One of hard-rule, soft-norm, likely-preference.
  • Confidence. How well-supported the rule is by the mined signal.

Doctrine mining runs asynchronously after installation (so we can respond to the install webhook fast). It re-runs incrementally as new PRs merge. Two repositories never share doctrine unless explicitly configured.

Model reasoning

After deterministic checks and doctrine retrieval, Ratify sends the model a structured prompt containing the diff, the doctrine rules that apply to this repo, and the deterministic findings that already fired. The model returns JSON in a strict schema (summary + array of findings, each with ruleKey, title, description, severity, confidence).

The prompt includes an explicit severity rubric so the model doesn’t undergrade obvious risks:

  • High: removed authentication, secrets committed, SQL injection risk, deletion of payment safeguards, obvious data-loss risk in a migration.
  • Medium: architectural violation, unapproved external dependency, API contract change without documentation, race conditions, memory leaks.
  • Low: debug leftovers, minor style/naming, missing JSDoc.

The reasoning call walks a fallback chain (primary large model → secondary smaller model → tertiary) so a rate limit on one free provider transparently falls through to the next. Every failure is logged with the specific upstream error, not silently swallowed.

The GitHub check & PR comment

Every review produces two artifacts on GitHub:

  • A check run on the head commit, with conclusion success (no findings), neutral (findings but none high), or failure (at least one high-severity finding). The check run body includes every finding with severity + source + confidence, plus a link back to the full Ratify review.
  • A PR comment with the risk score, the top three findings in collapsible details blocks, and a linkback to the dashboard for the full timeline. Only posted if findings actually exist — a clean PR gets a green check with no comment noise.

GitHub Actions workflow for deployment review

Ratify also reviews GitHub Deployments — useful if you want to gate production deploys on the same doctrine that gates PRs. The simplest way to opt in: drop this workflow at .github/workflows/ratify-review.yml in your repo.

Download the workflow YAML.

On every push to main, it creates a GitHub Deployment (via the built-in GITHUB_TOKEN, no external secrets needed). GitHub sends Ratify a deployment webhook; Ratify computes the delta since the last successful deployment to the same environment, runs the full pipeline, and posts a check_run to the deployment’s target SHA. Your actual deploy step can wait for that check.

Deployment webhook events

Ratify handles deployment events with the same pipeline used for pull requests, but with two differences:

  • The diff is previous successful deployment to this environment → new target SHA, not base branch → head branch. If there’s no previous deployment, we fall back to the target commit’s own diff.
  • The check_run is posted to the deployment’s target SHA (which is often main post-merge), so it shows up on the deployment view rather than a PR view.

Reacting to findings

On any finding in the dashboard, you can react with one of four verdicts:

  • 👍 Correct — the finding was on-target.
  • 👎 False positive — the finding was wrong; the code is fine.
  • Exception here — the rule generally applies but this specific case is an intentional exception.
  • Needs more context — the finding was ambiguous and Ratify should have said more.

Each verdict adjusts the finding’s confidence score (gently, clamped between 0.2 and 0.98) so future findings citing the same rule inherit a calibrated prior. One user’s disagreement doesn’t flip a rule off — corroboration across reviewers matters.

The pipeline timeline

Every review at /dashboard/{id} shows a full timeline: which stage ran, when, how long it took, and stage-specific detail (raw doctrine IDs retrieved, model finding count, deterministic rule keys that fired, etc.). This is what makes Ratify not-a-black-box: nothing in the review pipeline runs without leaving an inspectable audit row.

Data model

The primary tables:

  • users — Ratify accounts (Firebase UID, email, GitHub login).
  • organizations, installations, repositories — GitHub-side entities Ratify tracks. Every installation is org-scoped and can be owned by a Firebase UID for dashboard visibility.
  • pull_requests, review_sessions, findings — the review record. Unique index on (pull_request_id, head_sha) makes review sessions idempotent under webhook retries.
  • review_events — the pipeline timeline (webhook_received, policy_checks, context_retrieved, llm_call, evidence_generated, published, error, skipped_duplicate).
  • finding_feedback — user verdicts on individual findings, uniquely keyed per (finding, user).
  • doctrine_rules, doctrine_mining_runs — the per-repository rule store and mining audit log.
  • webhook_events — every GitHub delivery Ratify has received, keyed by GitHub’s X-GitHub-Delivery for dedupe.

How Ratify differs from generic AI review

Tools like CodeRabbit run an LLM over every diff and post inline comments. Ratify is a different shape of product:

  • Deterministic first, model second. Every finding starts with a real rule — not the model’s free-form opinion. The model reasons over evidence the backend already gathered, not the raw diff alone.
  • Repository doctrine, not generic best practices. Two identical PRs opened on different repos can (and should) get different reviews, because the rules are inferred from each repo’s own history.
  • Idempotent pipelines, not fire-and-forget calls. Duplicate webhook deliveries don’t produce duplicate reviews or duplicate PR comments. Every stage of the pipeline is auditable.
  • Feedback closes the loop. Marking a finding a false positive lowers the confidence of future findings from the same rule — the tool actually gets more accurate for your repo over time.
  • Deployment gating. Not just PRs; Ratify also reviews GitHub Deployments so you can hold production releases to the same standards.
  • Full transparency. Every review has an inspectable timeline showing which stages ran, in what order, with what duration and detail. Nothing happens in a black box.
